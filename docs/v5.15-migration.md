# V5.15 — migration, activation et retour arrière

## Référence immuable

V5.13 reste la référence stable. Ne pas modifier `release/v5.13` ni l'artefact identifié dans `releases/v5.13/REFERENCE.md`.

## Préconditions de production

Avant d'appliquer V5.15 :

1. Sauvegarder la base et conserver l'artefact V5.13.
2. Vérifier que l'année universitaire `2026/2027` existe et n'est pas archivée.
3. Créer dans le module Classes tous les groupes qui seront utilisés. Pour quatre groupes, V5.15 attend notamment les classes `MPI1-A-G1` à `MPI1-A-G4`, `MPI1-E-G1` à `MPI1-E-G4`, `MPI1-C-G1` à `MPI1-C-G4`, `MPI1-D-G1` à `MPI1-D-G4`, `MPI1-B-G1` à `MPI1-B-G4` et `PC1-A-G1` à `PC1-A-G4`.
4. Ne pas démarrer les anciens `session_plans` couvrant les dates qui doivent être remplacées par V5.15. Si l'un de ces plans a déjà créé une séance réelle, l'activation V5.15 sera refusée.
5. Les salles ne doivent pas être déduites automatiquement des fichiers Excel : leur correspondance Manipulation/Salle est contradictoire. L'Admin choisit explicitement une salle A, B, C ou D pour chaque affectation.

## Ordre des migrations

Appliquer exactement dans cet ordre :

1. `20260903150000_v515_planning_core.sql`
2. `20260903150100_v515_planning_grants.sql`
3. `20260903150200_v515_planning_rpcs.sql`
4. `20260903150300_v515_planning_2026_2027.sql`
5. `20260903150400_v515_admin_configuration.sql`
6. `20260903150500_v515_legacy_integration.sql`
7. `20260903150600_v515_request_cleanup.sql`

Les objets existants V5.13 ne sont pas réécrits par ces migrations.

## Activation fonctionnelle

1. Ouvrir `Planning V5.15` avec un compte Admin.
2. Initialiser le planning 2026/2027. Il est créé en `draft`.
3. Vérifier dates, alternances et rotations.
4. Configurer le nombre de groupes entre 1 et 6 avant matérialisation.
5. Configurer pour chaque enseignant son quota et les manipulations autorisées.
6. Publier le cycle. Les cycles incomplets M1–M6 génèrent des avertissements, pas un blocage de publication.
7. Les enseignants déposent leurs demandes.
8. L'Admin valide les demandes ou affecte directement les postes et choisit une salle A–D. Les conflits enseignant/salle, quotas et manipulations interdites sont contrôlés côté PostgreSQL.
9. Finaliser les affectations. La finalisation est refusée si un poste reste vacant ou si une classe/groupe requise pour la présence n'existe pas.
10. Cliquer `Activer dans présence`. Cette opération remplace uniquement les anciens plans non démarrés sur les dates explicitement présentes dans le calendrier V5.15 et crée les nouveaux `session_plans` utilisés par le flux V5.13 de présence/notes.
11. Vérifier dans le module présence que chaque séance planifiée expose la bonne classe, le bon groupe, l'enseignant, la manipulation, la salle et l'horaire.

## Protection des données existantes

`v515_materialize_session_plans` refuse l'opération si un ancien plan concerné a déjà été démarré (`session_id` non nul). Les séances réelles et leur historique de présence/notes ne sont donc pas remplacés.

Les jours `REPOS`, jours fériés et lignes `aucun TP` ne produisent pas de séance pédagogique et ne consomment pas un pas de rotation.

## Clôture pédagogique

La clôture du cycle se base sur les séances V5.13 réellement terminées reliées aux plans V5.15. Chaque groupe doit avoir réalisé M1 à M6 exactement une fois, sauf dérogation Admin enregistrée. Une duplication de manipulation réalisée bloque également la clôture.

## Retour arrière

Avant `Activer dans présence`, le retour arrière consiste simplement à désactiver l'interface V5.15 ou à retirer les objets `v515_*` selon une migration de rollback dédiée ; V5.13 reste intacte.

Après `Activer dans présence`, ne jamais supprimer directement les séances démarrées. Restaurer les plans uniquement à partir de la sauvegarde ou via une migration de rollback contrôlée. Les données historiques de présence et de notes restent prioritaires et ne doivent pas être réécrites.

## Gate de mise en production

Ne pas déployer V5.15 tant que :

- la CI de la branche n'est pas verte ;
- les sept migrations n'ont pas été exécutées avec succès sur une base de développement/staging ;
- les tests RLS/RPC réels n'ont pas été effectués avec un compte enseignant et un compte Admin ;
- le contrôle des classes/groupes de production n'est pas complet ;
- un test d'activation puis de démarrage d'une séance de démonstration n'a pas confirmé le raccord `v515_assignments -> session_plans -> sessions -> présence/notes`.
